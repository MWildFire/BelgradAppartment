## 3. Рабочие правила

- После команды пользователя на реализацию начинать с короткого preflight и конкретных исправлений W1/W2. Не останавливаться на новом списке рекомендаций. Чужие изменения сохранить; для изоляции использовать ветку `codex/…` или worktree по состоянию репозитория.
- Локальная реализация, тесты с временными БД и read-only диагностика не требуют повторного согласования рутинных деталей. Полномочия на деплой/рестарты сверять с актуальным запросом пользователя; не выдумывать согласование из этого документа и не переспрашивать уже разрешённое.
- Не отправлять людям тестовые Telegram/email-сообщения, не включать `deliver-all --force`, `rematch-all` или backfill с доставкой без соответствующего разрешения. Для тестов использовать fake transports/outbox.
- **`nightly-refresh` сейчас не read-only:** меняет БД, может скрывать карточки и отправляет сообщения. Не считать `--skip-sweep` запретом остальных записей/рассылок. Не придумывать существование общего `--dry-run`/`--no-notify`: сначала реализовать и доказать безопасный режим в W1/W3.
- Перед production-модификацией данных — проверенная согласованная копия. Не копировать только файл работающей WAL SQLite обычным `cp`; использовать SQLite backup API либо проверенный согласованный snapshot. Не заменять production локальной БД.
- Не делать прямого `UPDATE is_public=1` для всех 20 проблемных карточек: они уже public. Не публиковать непубличный primary и не менять глобальный dedup ради витрины.
- 403, 402, timeout, challenge и пропуск страницы не означают снятое объявление. Сайт не должен терять квартиру из-за возраста или одного проблемного источника.
- Не ослаблять тесты ради зелёного результата. Исключение: подтверждённо устаревшее ожидание PWA `/calculator` исправить на действующий продуктовый маршрут `/#lead`, с явной записью причины.
- Блокер live-доступа останавливает только зависимый live-этап. Локальные тесты, безопасные исправления и документацию продолжать. Не объявлять локальный PASS исправленным production.

## 4. Порядок и распределение работ

```text
W0 baseline / доступ / сохранение артефактов
 ├─ W1 безопасность обновлений + согласованный backup
 ├─ W2 публичная выдача дублей
 └─ W5a HTML escaping + проектирование публичных медиа
W1 → W3 proxy + quality metrics + scheduling + budgets + shadow
W1/W3 → W4 freshness + очереди + health
W2 → W5b media access + надёжная доставка/подписки
W1/W2/W3/W4/W5 → W6 release / canary / live acceptance
```

**Выпускать исправления поэтапно.** Готовую проверенную пачку P1 проводить через относящиеся к ней проверки W6 сразу после зависимостей: не откладывать защиту sweep и восстановление каталога до всех скрытых ошибок подписок. Каждый отдельный выпуск требует своего backup/совместимости/тестов/отката/live-проверки; общий статус остальных F-ID остаётся открытым.

Один integration owner владеет `src/cli.py`, `src/config.py`, DB migrations, общими интерфейсами, git-интеграцией и production. Независимо делегировать: A — data safety/readmodel; B — proxy/scrapers; C — воспроизведения и QA. Перед каждым batch зафиксировать точный ownership; `orchestrator.py` нельзя одновременно редактировать A и B. После W2 A переключается на delivery/media. Worker не использует production session/profile/DB; root передаёт безопасные результаты.

Субагент возвращает: F-ID, файлы/изменения, тесты/выходы, остатки, риски. Таймаут/молчание worker не означает PASS. Независимое ревью организовать для уже подготовленного diff; не превращать ожидание отдельного worker в бесконечную остановку всей локальной реализации.

## W1 · Безопасность обновлений и восстановления · F01/F02/F06/F07

**Файлы:** `src/cli.py`, `src/scrapers/orchestrator.py`, `src/site/liveness.py`, `src/db/models.py`, additive Alembic migrations, `scripts/restore_check.sh`; новые run/backup helpers по необходимости.

### Изменения

1. Явный результат источника: source/run ID, `crawl_complete`, причина остановки, pages attempted/failed/skipped, observed/processed/errors, denominator и доверие к нему. Качеством считать весь проход, а не наличие previews. Всегда возвращать результат упавшего источника.
2. Sweep допускается только по доказанно завершённому качественному полному обходу. Не называть 50%/70% безопасным по умолчанию. Если `site_total` сомнителен, сохранять записи и объяснять невозможность sweep, а не подгонять знаменатель.
3. Разделить source presence и разрешение снять публичную квартиру. Консервативная исходная политика: отсутствие подтверждается последовательными успешными полными проверками, согласованными с недельным периодом; не снимать по одному трёхдневному возрасту. Публичное снятие — только общая политика all-dead/pinned/warn-only/cap.
4. Все пути изменения публичности направить через одну функцию. Старый `verify-links` только записывает состояние ссылки и вызывает общую политику; закрепление и живые siblings учитываются везде.
5. Добавить реально безопасный preview/evaluation режим прохода: отчёт с причинами предполагаемых снятий, без listing/publication writes и без сообщений. Интерфейс CLI выбрать и задокументировать; тесты должны ловить любую случайную запись/доставку.
6. Backup: онлайн SQLite backup, manifest с временем/схемой/хешами/составом, DB/state/необходимые исходные и опубликованные медиа. Конфигурация и session для disaster recovery — только защищённое/зашифрованное хранение, не repo. Внешний storage выбрать из реально доступного; новый платный ресурс не создавать автоматически.
7. Restore drill проверяет возраст, schema/FK, ожидаемые ключевые таблицы, заявленный media manifest и запуск приложения в изоляции. Старый архив с одной пустой таблицей не должен давать PASS.

### Обязательные сценарии

- 100 previews / 100 item failures → failed/degraded, exit не success, нет sweep.
- 60% покрытия; HTTP 200 challenge на поздней странице; неверная пагинация; missing total; skipped pages → нет destructive sweep, есть причина.
- Отказ одного источника не запрещает полезную безопасную работу остальных, но весь запуск отражает деградацию.
- Первый 404 при pinned / живом sibling / warn-only / превышенном cap → карточка не скрыта.
- Полностью успешные проходы с подтверждённым отсутствием → снятие по новой политике, без регрессии нормального удаления.
- Dry-run запрещает все мутации и уведомления, не только stale sweep.
- Неполный/устаревший/без медиа backup → FAIL; полноценный backup восстанавливается и открывает карточку с фото.

**Тестовые точки входа:** `tests/test_nightly_steps.py`, `test_scrape_metrics.py`, `test_link_verify.py`, `test_site_liveness.py`, `test_orchestrator_reseen.py`; новые regression tests для восстановления/безопасного preview. Не привязывать полноценный backup PASS к успеху `quick_check` рабочей БД.

- Спроектировать выделенный public-media manifest/tree либо авторизуемую выдачу. Не закрывать сразу общий `/photos`, пока опубликованные карточки не обеспечены совместимыми ссылками. Не ограничиваться непредсказуемыми URL: требуется проверка разрешённой публикации.

### W5b — после интеграции контракта W2/public selection

1. Перенести/разрешить только реально опубликованные медиа; поддержать действующие URL опубликованных карточек. Проверить HEAD/GET неавторизованного доступа к одному известному unpublished fixture. Закрыть будущую выдачу; уже скачанные третьей стороной файлы нельзя отозвать, cache purge/expiry учитывать отдельно.
2. Outbox/delivery ledger на `(match, recipient)` и claim до отправки. Partial success повторяет только failed recipient. Не менять recipients и успешный Render Finder caption/media contract. При миграции старый общий `PublishedPost` не доказывает доставку каждому получателю: сохранить его как historical outcome, не превращать unknown в verified и не ставить весь исторический каталог в повторную отправку. Точечный repair прежней неполной доставки — отдельное обоснованное действие.
3. Не обещать абсолютную exactly-once сетевую доставку: timeout после фактического принятия сообщения провайдером создаёт `unknown` outcome. Явно решить reconciliation этого состояния, не делать слепой автоматический повтор.
4. Подписки: отсутствующая конфигурация не даёт sent, реальный транспорт возвращает подтверждённый результат. 24-часовое окно — лишь начальный отбор, далее постоянная очередь; 100 карточек/лимит30 и outage72ч не теряют остаток.
5. Один файл → sendPhoto, 2–10 → sendMediaGroup, ноль/недостающие файлы → явная диагностика без ложного успеха. Для tests API-double должен отвергать невалидный одноэлементный album.
6. PENDING 312 диагностировать адресно после изучения доставки; отсутствие inbound с 30.08 сверить с фактическим последним сообщением/watermark. Не исправлять предполагаемую потерю массовой повторной отправкой.

**Тесты:** `tests/site/test_leads_email.py`, `test_subscription_email.py`, `test_photos.py`, `test_photo_filter.py`, `tests/test_delivery_guard.py`, `test_notify_subscriptions.py`, `test_subscription_telegram.py`, `test_nightly_subscriptions_step.py`, `test_monitor_dedup.py`, `test_render_finder_zero_regression.py`; новые outbox/concurrency tests.

## W6 · Воспроизводимый release и доказанный production-результат · F15/F23 и все live gates

1. Единая версия release, явная целевая среда без старого VPS default; frozen dependencies, migration checks, canonical service/timer files + daemon-reload и сверка effective configuration. Разрешённые deployment действия выполнять одним operator.
2. Предпочитать additive schema; совместимость rollback версии приложения проверить заранее. Не делать автоматический destructive downgrade БД или restore старого backup после появления новых лидов/сообщений.
3. Подготовить deploy packet: exact revision/diff, тесты, backup/recovery manifest, изменения settings/units, признаки отмены rollout и команда/процедура отката без потери новых данных. Состояние допуска по текущей команде пользователя записать в status.
4. CI: unit + новые regression + shell syntax + changed-code lint. Существующие903 lint-замечания разобрать отдельно от P1, не ослаблять новые проверки. Browser e2e запускать отдельно в воспроизводимой среде с браузером нужной версии; исправить устаревший PWA тест. Системный Chrome прошлого ревью был диагностическим fallback, не обязательной будущей зависимостью.
5. После rollout проверить actual code hashes/revision, schema/FK, public endpoints/admin auth, реальные карточки/карту/media, timer command/timeout/next run. Убедиться, что monitor/site/admin используют согласованный код, а static не опережает процессы.
6. Bounded canary — только после нового безопасного eval/shadow и соответствующего разрешения записи; включить запрет внешних сообщений по реально реализованному интерфейсу. Сверить DB/public sets до/после. Snapshot active не включать автоматически как побочный эффект repair.
7. Контрольный полный проход с достоверными run outcomes и ещё один реальный автоматический запуск. Сохранять сведения о покрытии, item errors, успешной свежести, исключённых снятиях и доступности proxy. Восстановить историю мониторинга, чтобы следующий weekly был проверяемым.
8. Если до следующего автоматического запуска далеко, записать `deployed / manual verification passed / automatic verification pending`; не держать сеанс в многодневном sleep и не объявлять полное завершение. Автоматическое дальнейшее наблюдение создавать только в рамках актуальной просьбы пользователя.

**Release STOP:** необъяснённые потери public-квартир, скрытие pinned/UNKNOWN, изменение успешного caption/media/recipients, неполный backup, failing required tests, необъяснённый source coverage drop, утечка credentials. Устранять локально/откатывать безопасный app/config change; повторять gate после исправления, а не повышать пороги допустимых ошибок.

## 6. Что оставить следующему коллеге после каждого этапа

Открытые диагностические задачи выполнить ограниченно по доступным средствам; отсутствие доступа отразить как точный остаток:

| Проверка | Артефакт результата | Допустимый вывод |
|---|---|---|
| Источник Telegram vs watermark | Без текста/контактов: дата и ID последнего подходящего source message, watermark, наличие corresponding inbound | Нет новых подходящих постов / доказанный пропуск / нет безопасного доступа к источнику |
| PENDING 312 | Техническая причина, состояние match/publication/delivery, предлагаемый адресный repair | Ошибка установлена / историческая доставка неоднозначна; не инициировать массовый replay |
| AWS/B2 backup | Последняя дата/manifest существующей копии, состав, отдельный restore result | Backup+restore подтверждены / только файл существует / credentials недоступны |
| AWS Security Group | Inbound rules нужного instance без unrelated account data | Требуемые порты/источники разрешены / обнаружено конкретное лишнее правило / cloud access недоступен |
| ISP expiry/renewal | Без credentials: slot/order label, действительность, дата окончания, renewal status | Услуга актуальна / требуется продление / кабинет недоступен; не покупать по историческому quote |

Не выдавать просмотр последнего сообщения за проверку всего Telegram backfill; если есть разрыв, восстановление спланировать по диапазону и idempotency.

В `2026-09-08-implementation-status.md` записать: current branch/HEAD, изменённые F-ID, тесты и их результаты, exact deployed revision или «не деплоили», DB migration/backup, live evidence paths, remaining gates и **одно конкретное следующее действие**. Не затирать audit evidence новым состоянием — новые датированные evidence-файлы.

Статусы различать: `planned → in_progress → locally_verified → deployed → live_verified`; ожидание автоматического прохода отмечать отдельно. Пункт закрывать лишь при выполненных критериях; если cloud credentials/оплата/production authorization отсутствуют, назвать точный недостающий ресурс и продолжать независимое локальное.

Результат всей работы: все F-ID либо исправлены и проверены на соответствующем уровне, либо имеют явный остающийся внешний gate; завершение проекта не заявляется при скрытых pending gates.
