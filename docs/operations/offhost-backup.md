# Ежедневная резервная копия на Mac

Действующий порядок для `recovery.py`, `offhost_backup.py` и
`protected_recovery.py`. Полный формат восстановления описан в [recovery.md](recovery.md).
Рабочая схема на 10 сентября 2026 — `0014_group_availability_index`.

## Расписание и хранение

Установлен LaunchAgent `com.mvstrike.rentbelgrad-backup` пользователя Mac.
Его `StartInterval=21600` проверяет необходимость копии каждые 6 часов;
`RunAtLoad=true` выполняет проверку при загрузке задания, в том числе при входе
пользователя. Runner использует `--interval-hours 24`, а установленный plist —
`Umask=63` (восьмеричное `077`) и явный `WorkingDirectory` каталога кода.
Генератор `launch-agent` только печатает plist: его результат сам по себе не
подтверждает установку и не добавляет `Umask` или `WorkingDirectory`.

Копии находятся в `$HOME/Backups/RentBelgrad/offhost` на зашифрованном FileVault
диске пользователя. Приватные каталоги имеют права `0700`, файлы — `0600`;
исполняемые файлы runtime сохраняют право запуска владельцем. Данные и protected
часть разделены: `generations/<id>` и `protected/<id>`. Конфигурация и SQLite-сессии
не входят в обычный архив данных, репозиторий или журналы.

SSH-ключ задания хранится отдельно в `offhost/ssh/rentbelgrad-backup-key`, с правами
`0600` внутри приватного каталога. Проверка A/B 10 сентября установила: тот же ключ
из Downloads дважды не завершил SSH-canary за 35 секунд в launchd, а его побайтово
идентичная копия в приватном каталоге завершила проверку за 4,208 секунды.
Конкретный механизм macOS этой проверкой не установлен.

Runtime — отдельные `offhost/runtime/<SHA>/{code,venv}` из точного Git SHA и
`uv sync --frozen --no-dev --no-editable`; проверяются lock, импорты, схема и
неизменность исходных файлов. Запущенный runtime не редактируют. На момент подготовки
документа задание использует `2fb3971`; `8756a6d` подготовлен и проверен отдельно.
Переключать Python, script path, `--application-project-root` и `WorkingDirectory`
нужно согласованно после завершения текущего процесса. Актуальные пути берутся из
установленного plist, а не из текущего рабочего checkout.

## Что считается принятой копией

| Результат | Значение |
| --- | --- |
| `snapshot_staged_not_verified`, `protected_snapshot_staged_not_verified` | Только исходный staging; восстановления на Mac ещё нет. |
| `prepared_metadata_checked_not_restored` | Проверен manifest готового staging; это не проверка всех данных. |
| `pending/<id>` или `protected-pending/<id>` | Незавершённая либо неуспешная работа. |
| `data_restore_verified` и связанный локальный receipt | Данные приняты после проверки файлов и изолированного восстановления. |
| `skipped_locked`, `skipped_not_due` | Runner сработал, новую копию не создал. |

Для принятой полной пары нужны каталог поколения и `receipts/<id>.json` с
`offhost_verified=true`, `backup_format=directory_generation`, совпадающими
`manifest_sha256` / `generation_manifest_sha256`, исходной датой создания и ожидаемой
схемой. Проверка приложения включает каталог, карточку и декодирование фотографии.

`protected_recovery_verified=true` и свежий `protected_proof` должны относиться
к этому же поколению и manifest данных. Проверяются шифрование, права, точный набор
компонентов, размеры/SHA-256, конфигурация, целостность SQLite/FK и наличие материала
авторизации. Это проверка сохранённых файлов: `live_authentication_checked=false`.

При включённом `--publish-health-receipt` после локальной проверки атомарно публикуется
`/opt/otz/data/state/recovery_receipt.json`. Оператор сопоставляет его с локальной
копией: ID, дату, schema revisions, manifest hashes, результаты приложения и protected
проверок. `health_receipt_published=false` означает, что локальная пара сохранена,
но серверное подтверждение не обновилось. Старый receipt не получает новую дату.
Предельный возраст для текущего recovery gate — 36 часов.

## Продолжение работы и canary

1. Прочитать последние локальные receipts, журналы и состояние задания. Убедиться,
   что прежний процесс завершился, прежде чем менять runtime или запускать новую
   работу. Существование PID, staging или пустого pending не означает успех.

   ```sh
   plutil -lint "$HOME/Library/LaunchAgents/com.mvstrike.rentbelgrad-backup.plist"
   launchctl print "gui/$(id -u)/com.mvstrike.rentbelgrad-backup" \
     | rg '^\s*(state|pid|runs|last exit code) ='
   ```

2. Сверить зашифрованное хранилище, приватные права и проверенный runtime с текущей
   схемой. Для SSH-canary использовать тот же UID и обычный фоновый контекст launchd,
   Python, каталог, ключ и SSH-параметры установленного задания. Удалённая команда —
   только `/usr/bin/true`; ограничение отдельной проверки — 35 секунд. Зафиксировать
   длительность и код завершения, без вывода ключа, конфигурации или полного argv.
   Успех из интерактивного терминала не заменяет эту проверку контекста.

3. Если прежний исходный snapshot **завершился с кодом 0**, допускается одноразовый
   `offhost_backup.py run` с прежними проверенными аргументами и обеими опциями
   `--prepared-snapshot-dir` и `--prepared-snapshot-manifest-sha256`. Путь — прямой
   `.manual-*` или `.offhost-*` потомок `/opt/otz/data/backups`, manifest закреплён SHA-256,
   его возраст не превышает 36 часов, writer уже завершён. Runner под новой remote
   lease сам вызывает `check-snapshot-metadata`, затем повторно проверяет переданный
   manifest, все локальные файлы и восстановление; protected часть создаётся заново.
   Эти опции не включают в recurring plist. Если staging неполон или устарел, нужен
   новый исходный snapshot; pending вручную не переименовывают в accepted.

4. Для повторной проверки данных принятого поколения взять ID и схему из его receipt,
   а `OFFHOST_ROOT` — из установленного задания. `OFFHOST_RUNTIME` должен соответствовать
   схеме выбранной копии: старую копию проверяют совместимым сохранённым runtime.
   Значение `EXPECTED_SCHEMA` согласуется с receipt и проверенным кодом; для новой
   текущей копии это `0014_group_availability_index`.

   ```sh
   "$OFFHOST_RUNTIME/venv/bin/python" "$OFFHOST_RUNTIME/code/scripts/recovery.py" \
     verify-directory "$OFFHOST_ROOT/generations/$GENERATION_ID" \
     --application-project-root "$OFFHOST_RUNTIME/code" \
     --expected-schema "$EXPECTED_SCHEMA"
   ```

   Команда проверяет данные и запускает изолированное восстановление. Protected часть
   отдельно проверяет `protected_recovery.verify()` с ID, hash/датой данных и точным
   набором session aliases из действующих параметров; runner вызывает её автоматически.
   У `protected_recovery.py` нет отдельной CLI-команды `verify`.

5. Подтвердить автоматическую работу по реальному запуску launchd, его времени и
   завершению, **новому принятому поколению** и соответствующему серверному receipt.
   Первое успешное создание через `RunAtLoad` записывается именно как `RunAtLoad`;
   последующий запуск по интервалу подтверждается отдельно. Ручной `run` или
   `kickstart` — операторский запуск. `skipped_not_due` после смены runtime подтверждает
   вызов нового runner, но не создание им новой копии.

## Неуспешный запуск и срок актуальности

В новом runner ошибка содержит только `phase`, `error_type`, `returncode` и
`accepted=false`; исходная причина сохраняется даже при последующей ошибке закрытия
соединения. Старый общий `backup_failed` не позволяет восстановить этап задним числом.
Пустой pending возможен при ошибке lease, исходного snapshot или первого переноса.

Неуспешные pending сохраняются для разбора; после успешного завершения остаются две
последние принятые пары. Незавершённая работа не вытесняет последнюю хорошую копию.
Копия со старой схемой или без требуемой свежей protected/server proof не становится
актуальной только потому, что ещё не истекли 24 часа.

Сон, выключение или отсутствие сети на Mac могут отложить запуск. `RunAtLoad` не
является гарантией запуска при каждом пробуждении, а расписание само по себе не
гарантирует копию моложе 36 часов. Просрочку определяют по исходной дате последнего
подтверждённого поколения. Начатое 10 сентября поколение `20260910-080628-2989418e`
нельзя объявлять принятым на основании одного сообщения о запуске.
