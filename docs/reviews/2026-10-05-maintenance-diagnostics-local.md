Продолжение существующей задачи `01a0f2be-7d58-7da3-a6f5-a3fdedadd0f6`.

## Что исправлено

У public-detail refresh были `errors > 0`, но пустой `source_errors`: причины отдельных
карточек терялись при формировании checkpoint. На сохранённом снимке штатного запуска
19:03–19:04 UTC подтверждено 16/19 карточек, три ошибки; восстановить их точные причины
задним числом невозможно. Новая диагностика начнёт работать только после отдельного выпуска.

`DetailRefetchStats` и `data/state/freshness/{refetch,public_refetch}.json` теперь содержат
`reason_counts[platform][stage][code]`. Причина учитывается для каждой неудачной/пропущенной
карточки, но сохраняются только агрегаты: без IDs, URL, контактов, текста объявления,
произвольных сообщений и имён классов исключений. Набор площадок, этапов и кодов ограничен.

| Этап | Что считается |
| --- | --- |
| `item` | Неуспешные реальные попытки карточек: timeout, неполные поля/фото, mismatch, HTTP, browser/proxy и т. п. |
| `skipped` | Не начатые попытки после ошибки источника, нехватки бюджета/отмены, либо удалённая из БД карточка |
| `source` | Ошибки контекста/бюджета источника; это события, а не дополнительные неудачные карточки |
| `persistence` | Ошибки записи результата попытки; исходная причина карточки сохраняется отдельно |

**Суммировать все этапы как число ошибочных карточек нельзя:** `source` и `persistence`
могут описывать те же события, которые уже затронули `item`/`skipped`.

Причины записываются по мере работы, включая источник перед переходом к следующему.
Отмена позже в очереди не стирает уже известную ошибку. Внутренняя отмена из `asyncio.timeout`
приводится к `timeout` после выхода из timeout-контекста; внешняя отмена остаётся `cancelled`.
Успешный SQL commit, завершённый при отмене, остаётся успешным и не создаёт ложную ошибку.
Карточки, не начатые к отмене, теперь явно входят в `skipped`, без ложной записи попытки в БД.

В существующем admin health выводятся безопасные коды и количества. Старые checkpoint без
нового поля продолжают читаться; это не восстанавливает отсутствовавшие причины.
Некорректные diagnostics не отображаются и не позволяют показать успешное завершение.
Неизвестные legacy source exception names заменяются на `RefreshError`.

Сохранены retry/backoff, подтверждение freshness только по реальным данным/фото, exit 1
при ошибках и неполном покрытии, запрет destructive sweep на недостоверном обходе.
Исправлено только устаревшее описание nightly CLI: canonical daily и weekly units используют
full mode; сами параметры, расписания, ограничения прокси и бюджеты не менялись.

Код для review: `src/scrapers/refresh_diagnostics.py`,
`src/scrapers/orchestrator.py::refetch_listing_details`,

## Отдельный локальный preflight backup

Добавлен `scripts/data_only_preflight.py`. Он **не подключён к offhost job** и не умеет
SSH/rsync, передачу, ротацию generations, protected recovery, публикацию health receipt или
загрузку launchd. Проверялся только на синтетических данных. Настоящая БД и секреты в этом
этапе не читались; штатный runtime helper, plist и fallback не изменялись.

Инструмент создаёт в новом приватном каталоге консистентную копию `data/otz.db` через SQLite
online backup, затем уплотняет только эту копию (`VACUUM`), чтобы не переносить свободные
страницы с удалёнными данными. Проверяет schema/integrity/FK и выполняет ограниченную
credential inspection до принятия локального пакета. Секретные значения в диагностику не
попадают. При ошибке временная созданная копия удаляется; существующий output не перезаписывается.

Scope изображений: DB-referenced `data/inbound` originals и их известные `.card.webp`/
`.detail.webp` варианты; для legacy listings — фото в каталогах `data/listings/<platform>/<id>`,
чья identity присутствует в БД. Внутри такого legacy album сохраняются все допустимые фото:
полная пофайловая принадлежность старых альбомов в БД отсутствует. Orphan directories
исключены. Поддержаны только штатные `data/inbound` и `data/listings`; отдельный произвольный
published root намеренно отклоняется, его нельзя подключить без нового review scope.

Фильтр допускает только JPEG/PNG/WebP, запрещает symlink, обход каталогов, скрытые и
credential-like имена, state/logs/config/session/key/cookie файлы. Проверяет SHA-256,
стабильность stat, формат и полный decode изображения. Исходный `photo_manifest.json`
не читается и не копируется: это произвольный индекс, который нужно будет безопасно
пересоздать в будущем restore workflow.

Credential gate блокирует заполненные поля/таблицы с именами token/secret/password/api_key/
auth_key/session/cookie и несколько известных форматов credentials в TEXT/BLOB и байтах изображений.
Это намеренно консервативно: даже временный lease/claim token требует отдельного решения.
Ограничения: 256 таблиц/колонок, 8 MiB на значение, 8 GiB сканируемых значений,
32 MiB / 40 MP на изображение; превышение блокирует результат. Производительность на
production-объёме не измерена.

**Это эвристика, не доказательство отсутствия секретов.** Неизвестный/закодированный токен,
произвольный текст и текст внутри картинки могут её пройти; OCR нет. БД сохраняет личные
данные, не обезличена и не очищается автоматически. Отсутствие subscription rows в прежнем
снимке не переносится как допущение на будущий экспорт.

Формат `renfinder-db-media-preflight-v1` специально несовместим с действующими recovery
receipts. Результат содержит `offhost_verified=false`, `protected_recovery_verified=false`,
`health_receipt_published=false`, `authorization_to_transfer=false`. Медиа только проверены
и перечислены; не скопированы. Это **не backup и не подтверждение восстановления**.

## Что остаётся на следующий согласованный этап

1. Review этого diff и отдельное решение о commit/push/CI и выпуске maintenance-диагностики.
   До решения — только локальные изменения; модель и provider не меняются.
2. После согласованного выпуска — дождаться штатного refresh и проверить новые причины,
   accounting и отсутствие данных пользователей в checkpoint. По ним выбрать исправление
   источника. Само добавление диагностики не чинит coverage/proxy/browser failures и не
   доказывает улучшение качества или скорости. Повышать платные proxy budgets автоматически нельзя.
3. Для backup сначала отдельно согласовать **source-side inspection без переноса**. Затем
   показать owner безопасный результат/ограничения и согласовать конкретный DB+media scope,
   персональные данные, остаточный credential risk и отдельный destination namespace.
   Если scope не проходит, подготовить отдельный явно согласованный sanitised export,
   а не удалять/редактировать production данные.
4. До любого нового переноса ещё нужны transport integration с общей source lease,
   immutable/pinned source inventory, повторная проверка bytes до egress и на receiver,
   регенерация photo index, offline application restore, отдельные receipt/retention/namespace.
   Preflight manifest нельзя передать в прежний full helper как обход отказа.
5. Не повторять отклонённый полный job с credentials. Он был выгружен в предыдущем этапе,
   plist не изменён и может загрузиться при новом Mac login. В этом этапе launchd не трогали;
   постоянное отключение/перенастройка требуют отдельного решения владельца. Предрелизная
   проверенная копия остаётся прежней; успешный postmigration backup здесь не получен.

Причина остановки переноса: предыдущий automatic approval review отклонил запуск full backup,
поскольку переданное широкое согласие не было принято как прямое подтверждение переноса
production DB/media и защищённых config/session credentials. Этот локальный preflight не
снимает отказ и не является новым разрешением. Ночного запроса пользователю не отправляли.

В текущем local-only этапе нет запросов к площадкам, модельных API, новых ключей/подписок,
платных тестов или отправки сообщений. Library не обновлялась: прежняя версия PDF v5
описывает release/triage, а этот новый diff и результаты пока доступны локально.
