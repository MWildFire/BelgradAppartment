## Почему простое удаление 43 элементов массива непригодно

`src/scrapers/orchestrator.py:719` сохраняет фото под индексами массива; `_guess_extension` определяет расширение по URL. `src/admin/routes.py:834` ограничивает доступ длиной `photo_urls`, затем читает файл с этим индексом. `src/matching/identity.py:57` и `src/matching/dedup.py:265` используют длину массива как число фото.

Если просто убрать элементы, сохранив файлы и остальную БД, 43 существующих индекса станут недоступны в админке, у двух записей исчезнет весь альбом, а 56 оставшихся URL поменяют позицию относительно файлов. Ранее предложенный вариант удаления элементов отзывается как функционально неполный; к данным он не применялся.

Предлагается только в согласованной копии заменить каждое из 43 выбранных значений `photo_urls[i]` на `restore-local:///NNN.ext`, где NNN — прежний индекс, ext — прежнее каноническое расширение. Сохраняются длина/порядок всех массивов, 147 файлов, pHash, embeddings, photo_evidence, остальные поля и все остальные записи. 104 незатронутые внешние ссылки остаются неизменными. 43 исходных URL не включаются в журнал, manifest или mapping.

Это локальный маркер, который нельзя скачать по HTTP. Потеря остаётся конкретной: 43 исходных внешних адреса, у двух записей — все внешние адреса фотографий. Доступ к уже сохранённым фото и существующему evidence сохраняется. Восстановление полноценного сетевого повторного скачивания требует отдельного обновления данных из исходного listing URL; до такого обновления нельзя запускать `hash-listings` для попыток скачивания этих маркеров. Текущий backup/restore scope остаётся offline; никаких сервисов/таймеров восстанавливаемой копии автоматически не включать.

Прототип находится вне release tree: `readiness/media-release-20261006/sanitization_prototype.py`. Он выполняет только чистое преобразование в памяти, не открывает БД/файлы/сеть и не подключён к production backup. Количество строго ограничено пятью ячейками/43 значениями; дрейф, другой домен, userinfo, query, непредусмотренный provider prefix или неверный тип приводят к отказу. Полный обычный scanner после преобразования обязателен и не ослаблен.

## Процедура после отдельного согласования потерь

1. На сервере получить новый согласованный snapshot и проверить актуальные число/категории совпадений; отклонить изменение объёма или контекста.
2. Проверить канонические файлы и согласованность pHash/embeddings каждого заменяемого индекса; прекратить процесс при изменении/отсутствии файла.
3. В транзакции **копии** заменить только выбранные URL-значения маркерами с теми же индексами/расширениями. Сравнить все прочие колонки/таблицы и row counts; сохранить только агрегаты diff. Production БД не редактировать.
4. VACUUM только копии; integrity/FK/schema; полный credential scan всех TEXT/BLOB и всех переносимых фото. Не сохранять удалённые значения в sidecar и не экспортировать snapshot при любом отказе.
5. Проверить DB-reference allowlist, полное decode и SHA каждого файла, создать отдельный честный scope `db_media_sanitized` с количеством замен и потерями. Старый `db_media` receipt для него не использовать.
6. После успешного gate — разрешённый data-only перенос и restore без сети. Проверить настоящие catalog/apartment/photo routes и все пять listing-альбомов; ничего не включать в production.

Отдельное согласование именно замены/потери 43 URL ещё не получено. Общее «продолжай» не трактуется как ответ на этот конкретный вопрос. Прямое разрешение на исходную одну DB+media копию по-прежнему действует и не запрашивается повторно.
