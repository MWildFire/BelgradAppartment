# ADR — Публичный веб-каталог @RentBelgrad

> Статус: **принято** · Дата: 2026-06-20 · Этап: **Stage W — «Public Web Catalog»**
> Контекст: `HANDOFF.md`, `docs/SPEC.md`, дизайн-архив (`design/`). Этот ADR — основание для плана
> `docs/superpowers/plans/2026-06-20-public-web-catalog.md`.

## Решение в одну строку

Публичный каталог — это **второе FastAPI+Jinja-приложение на той же VPS**, читающее **существующую SQLite read-only**, под **Caddy** (авто-TLS). **Не** Astro/Vercel/Node и **не** повторный ингест из Telegram.

## Почему так (а не как в дизайн-плане)

Дизайн-архив (`design/DESIGN_PLAN.md`, бывш. `CLAUDE_CODE_PLAN.md`) предлагает Astro 4 + Vercel + Vercel Blob + Drizzle + повторный ингест канала через Bot API/Playwright. Для этого проекта это неверно по четырём причинам:

1. **Одна машина, один тулчейн.** Проект — Python 3.12 / FastAPI / Jinja / HTMX / SQLite / Alembic / systemd, деплой **rsync без git на сервере**. Админка уже живёт как FastAPI+Jinja+HTMX на `127.0.0.1:8000`. Второй FastAPI-сервис встаёт в каждый существующий паттерн (systemd-юнит, `deploy_sync.sh`, alembic, pytest). Astro+Node+npm+Vercel — это второй рантайм и сборочный пайплайн на машине, которая деплоится rsync'ом. Операционный мисматч.
2. **Данные уже есть.** Фаза 3 дизайн-плана (читать `t.me/s/RentBelgrad`) — избыточна: система уже скрапит площадки, матчит и пишет опубликованных кандидатов в SQLite (`listings`, `matches`, `published_posts`). Каталог читает оттуда. Нулевой новый ингест.
3. **ToS / политика проекта.** Риск-строка SPEC §8: *«Не публикуем результаты скрапинга наружу, используем как метаданные»*. Значит публичный каталог **не** показывает сырые 21.8k listings и **не** линкует на площадки-конкуренты. Он показывает только **отобранные Дарьей** квартиры, которые уже опубличены в @RentBelgrad. Это требует флага курирования под контролем Дарьи (расширение admin-действий из этапа H1) — это фича, а не просто запрос.
4. **Дизайн сохраняется 1-в-1.** `tokens.css` + `index.html` — вёрстка на **ванильном CSS с custom properties**, не Tailwind. Значит Tailwind из дизайн-плана **не нужен**: токены и компонентный CSS отдаются Jinja напрямую. Ещё проще.

**Что из дизайн-плана сохраняем дословно:** раздел 0 (анти-AI-slop закон), палитру, типографику, геометрию, микрокопирайт, список «вкусовых» скиллов для ревью (`taste`, `impeccable`). **Что отменяем:** разделы 1 (стек), 3 (ингест), хостинг Vercel/Blob. Дизайн-эталоны (`design/index.html`, `design/RentBelgrad Design System.html`, `design/reference.png`) — источник правды для внешнего вида.

## Источник данных каталога

Публичная карточка = `Match(status=PUBLISHED)` + флаг **«на сайт»**, отображаемый через тонкий read-model. Чтобы **полностью развязать** публичный сайт и внутренний пайплайн, вводим отдельную таблицу-оверлей:

- **`site_listings`** — одна строка на публично выставленную квартиру: `match_id (UNIQUE FK)`, `is_public`, `is_for_vnj`, `is_for_white_card`, `channel_post_url (nullable)`, `note (nullable)`, `created_at`, `updated_at`. Всё остальное (цена/площадь/комнаты/район/координаты/фото) — джойном к `listings`.
- **`leads`** — заявки на персональный поиск из формы сайта: `id`, `created_at`, `name`, `contact`, `budget_eur`, `districts`, `rooms`, `message`, `source='site'`, `status`.

Это CQRS-овый read-model: пайплайн пишет свои таблицы, сайт читает курированный оверлей. Изменения в пайплайне не ломают сайт; ошибка сайта не трогает пайплайн.

**Дефолт видимости:** при admin-действии «Mark-posted» (H1) ставим `is_public=true`, если Дарья не сняла галочку. Видимость и флаги ВНЖ/картон Дарья переключает в админке.

**Ссылка с карточки → на канал @RentBelgrad**, не на площадку (ToS). Per-post deep-link в канал отложен: в bot-mode `published_posts.tg_message_id` = id доставки в чат бота (Дарья постит вручную), реального id сообщения в канале у нас нет. Поле `channel_post_url` опционально заполняется Дарьей в админке для точных ссылок; иначе — ссылка на канал целиком.

**Фото:** локальные копии уже скачаны на VPS (TG-CDN протухает — у нас свои файлы). Отдаём их статикой через Caddy `file_server` (а не через Python на каждый запрос).

## Топология на VPS

```
                 Caddy (:80/:443, авто-TLS Let's Encrypt)
                 ├─ /static/*  /photos/*  → file_server (диск, far-future cache)
                 └─ /*                     → reverse_proxy 127.0.0.1:8001
                                              (otz-site.service, uvicorn, User=otz)
127.0.0.1:8000  Admin (otz, read-only, basic auth) — НЕ проксируется, остаётся localhost-only
SQLite WAL (/opt/otz/data/otz.db)
  ├─ публичный app: read-only engine (PRAGMA query_only) для каталога
  └─ публичный app: узкий writer для write-аллоулиста `leads` + `subscriptions` + `site_events`
     (append-only телеметрия, Stage T контракт §0; busy_timeout=5000, retry)
otz-monitor / nightly / Outline VPN — без изменений, порты не пересекаются
```

**Безопасность:**
- Публичный app слушает `127.0.0.1:8001`; наружу — только через Caddy. Админка (:8000) наружу **не выставляется никогда**.
- Публичный app не имеет write-доступа к пайплайн-таблицам: read-only engine для чтения + отдельный scoped-writer, чей write-аллоулист — `leads` + `subscriptions` + append-only `site_events`-телеметрия (Stage W2 добавил `subscriptions`, Stage T — `site_events`, осознанное решение D1/контракт §0). (Опция строгой изоляции, если захотим: вынести эти таблицы в отдельный `data/site.db`. На MVP — единая БД + least-privilege engine.)
- ufw: открыть `80`, `443`. Outline (`50029`, `28395`) не трогаем — конфликта нет.
- Никаких аккаунтов клиентов в MVP. Избранное — `localStorage`. Форма заявки — только запись в `leads` + нотис Дарье через существующий бот.

**Перфоманс:** каталог меняется редко (несколько публикаций/день). In-app TTL-кэш результатов каталога (~5 мин) + `Cache-Control` на статику/фото через Caddy. Публичный трафик не конкурирует с матчером за CPU (чтения дешёвые, WAL допускает много читателей).

## Что в MVP и что нет

**В MVP (совпадает с веб-экранами дизайн-системы):** главная · каталог с фильтрами (ВНЖ, белый картон, район, цена, комнаты, сортировка, пустое состояние) · карточка `/apt/{id}` (галерея, параметры, блок «важно для релокантов», CTA, ссылка на канал) · карта (Leaflet + кластеры) · калькулятор аренды · форма заявки (→ `leads` + нотис) · избранное (`localStorage`).

**НЕ в MVP (отложено, зафиксировано чтобы не потерять):** аккаунты/профиль клиента · WebGPU-hero (в дизайн-плане по умолчанию выкл) · per-post deep-links в канал (до заполнения `channel_post_url`) · тёмная тема · мультиязычность (сайт на ru; i18n — отдельный этап).

## Альтернативы, которые отклонили

- **Astro/Vercel (дизайн-план):** второй рантайм + хостинг вне VPS + повторный ингест. Отклонено (см. причины 1–3).
- **Расширить админку публичными роутами:** смешало бы localhost-only админку (basic auth) с публичным трафиком в одном процессе/порте. Риск утечки админ-функций. Отклонено в пользу отдельного app.
- **Отдавать все 21.8k listings:** нарушает ToS-политику и обесценивает курацию Дарьи. Отклонено в пользу `site_listings`-оверлея.
